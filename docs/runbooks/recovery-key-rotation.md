# Runbook — Recovery-key (D6) rotation

**Status:** Phase 6 (ops). Implements `DESIGN.md` §16.4 (recovery-key rotation) / §16.3 (custody) / §6.3.
**Owner:** the D6 custodian, on the air-gapped recovery machine.

> **Scope.** D6 is the all-files escrow (§1.2/§6.3). Rotation is a deliberate, expensive **re-wrap project**, not an emergency action — plan it. Trigger it on suspected D6 compromise/theft, on a custody change, or as scheduled hygiene.

> **CORRECTION 2026-08-01 — steps 1, 2, 4, 5 and the custody section below described a RETIRED design.** This runbook previously instructed the operator to call `split_recovery_key` / `reconstruct_recovery_key` over `crypto::shamir` and to distribute K-of-N custodian shares. **Those functions do not exist.** The K-of-N Shamir custody model was retired with T6 (spec `2026-07-03-trusted-server-recovery-registration-design.md` §8; `crates/crypto/src/shamir.rs` is deleted and `admin-core` exports only `build_recovery_grant` / `validate_recovery_wrap`, alongside `sweep::run_sweep`). **What actually exists:** the recovery private key is **one Argon2id-sealed cold file**, `recovery_key.blob`, sealed by `keyblob::seal` over the whole recovery `Identity` (`tools/maxsecu-setup` `setup.rs::seal_recovery_blob`) and opened with its passphrase — no shares, no custodians, no reconstruction step. The steps below are corrected accordingly; the struck-through text is kept for provenance. **Note also that no shipped tool automates D6 rotation:** `maxsecu-setup`'s subcommands are `fetch-pins`, `restore` and the delegation `renew` path (`main.rs:26`, `setup.rs::RenewOpts`) — it mints the recovery key **once**, create-new, at install. Rotation is a hand-run project against the air-gapped machine. A threshold split is future work (`DESIGN.md` §19), not a shipped property.

## Steps (from §16.4)
1. **Generate** a new D6 keypair (X25519) on the air-gapped machine, then **immediately Argon2id-seal the new private key as a single cold blob** — the same `keyblob::seal` shape `maxsecu-setup` writes for `recovery_key.blob` (`setup.rs::seal_recovery_blob`), so the new file is a drop-in replacement for the old one. Choose a strong, independently-custodied passphrase; the seal is the **only** barrier on the blob. Store the blob and a sealed backup under dual-custody witness. ~~**immediately split the new private key K-of-N** for custody: `split_recovery_key(&new_recovery_priv, k, n)` → one `Share` per custodian (the scalar is exposed only transiently on the offline device and zeroized; §16.3). Choose `k`/`n` per policy (e.g. 3-of-5). Distribute one share to each custodian under dual-custody witness. **No whole cold copy of the new key is retained.**~~
2. **Unseal the OLD key** for the re-wrap work: open the old `recovery_key.blob` with its passphrase to recover the old `recovery_priv` in air-gapped RAM (or recover DEKs via current holders). A wrong passphrase or a corrupt blob fails closed — abort. ~~**Reconstruct the OLD key (threshold)**: `k` of the old custodians convene and `reconstruct_recovery_key(k, &old_shares)` rebuilds the old `recovery_priv` in air-gapped RAM.~~
3. **Re-wrap the recovery recipient across files** as a background project: for each file-version, recover the DEK with the reconstructed **old** `recovery_priv` (or via a current holder) and add a fresh `recovery` wrap to the **new** recovery public key. This reuses the §12.7 re-wrap path (`build_recovery_grant`-style re-wrap) and the sweep machinery to track coverage (`recovery-wrap-sweep.md`).
4. **Validate** new wraps with the **new** `recovery_priv` (unsealed from the new blob) via `run_sweep` before retiring the old key — confirm every re-wrapped version opens to its committed DEK (R26 discipline). Zeroize both unsealed keys when the work is done. ~~(threshold-reconstructed from the new shares)~~
5. **Retire the old key** only once coverage is complete and validated; then **destroy the old `recovery_key.blob` and every backup copy of it** under dual-custody witness (§16.3). Because there is no threshold, retiring the old key means accounting for **whole copies** — inventory them first; one forgotten backup plus its passphrase is still a full escrow. ~~have each old custodian **destroy their old share** under dual-custody witness (§16.3) — no whole old key need ever be reassembled to retire it.~~
6. **Re-pin** the new recovery public key as the standing directory recovery entry (verified like any binding, §7.2) so new uploads wrap to it.
7. **Audit** the rotation project (coverage, validation, share distribution, old-share destruction) to the external sink (§16.5).

## Custody (§16.3)
- D6 is **one Argon2id-sealed cold blob** (`recovery_key.blob`) plus its passphrase, kept cold, dual-custody, access-logged (corrected 2026-08-01). **A single stolen copy plus its passphrase is total** — there is no `k-1` margin, and no share to lose. The key is unsealed into RAM at every use, and since the 2026-08-01 amendment (`DESIGN.md` §6.3) that use is **no longer air-gapped-only**: the same blob can be loaded on a networked client for an online recovery session, which reads and can grant every file. Air-gapped custody is the **recommended** model, not the only one (`recovery-session.md`). ~~D6 is **split K-of-N across custodians** (Shamir, Phase 7 / P7.7 — `split_recovery_key`/`reconstruct_recovery_key`, §16.3/§19): each share is kept cold, sealed, dual-custody, access-logged. **No single share — or any `k-1` shares — is total.**~~
- Note that `maxsecu-setup` seals **D5 and the recovery key under the SAME passphrase** at install (`setup.rs::RenewOpts` — "the recovery passphrase; unseals BOTH the D5 blob and the recovery key blob"). Rotating D6 onto a fresh, independent passphrase is what actually separates the two custodies; keeping the shared one means one passphrase disclosure reaches both.
- Keep D5 and D6 on **separate** cold devices (§3.1 M-5). If a single vault that held both is compromised, rotate **both** (this runbook + `emergency-d5-rotation.md`).
